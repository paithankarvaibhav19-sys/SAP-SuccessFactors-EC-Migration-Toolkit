## 1. Business Objective & Scope

This specification defines the field-level architecture, custom extensions, and automated business rules for the `jobInfo` (Job Data) element. It translates standard PeopleSoft operational fields into SAP SuccessFactors Employee Central, supporting both Regular Employees and Contingent Workers while automating manager derivation and role-domain governance.

## 4. Automated Business Rules & Logic

### Rule 1: Dynamic Department-to-Global Manager Auto-Population
* **Trigger Event:** `onChange` on `department` field in `jobInfo`.
* **Condition:** When Department is selected or changed.
* **Action:** Automatically set `manager-id` to the designated Head of Department (HOD).

---

### Rule 2: Business Role to People Function & Domain Derivation
* **Trigger Event:** `onChange` on `custom-string3` (Business Role).
* **Rule Workflow:**
  1. If a standard role mapping exists, automatically populate **People Function** and **People Domain**.
  2. If no standard mapping exists (custom or specialized role):
     * Check if **Deviation Required** is set to **Yes**.
     * If **Yes**, default both **People Function** and **People Domain** to `"To Be Defined"`.

```text
[ Business Role Selection ]
        │
        ├── Standard Mapping Found ───> Populate People Function & Domain
        │
        └── Non-Standard / No Mapping ─> Check "Deviation Required" Flag
                                            │
                                            ├── IF Yes ──> Set Function & Domain to "To Be Defined"
                                            └── IF No  ──> Block Save / Throw Validation Error

## 3. Deep-Dive: XML Data Models & Architecture

In SAP SuccessFactors Employee Central, foundational configuration involves two primary data models managed via Provisioning: the **Corporate Data Model (CDM)** and the **Succession Data Model (SDM)**, alongside their Country-Specific counterparts (CSF).

---

### 3.1 Data Model Classification Matrix

| Data Model | File Name | Primary Purpose | Scope |
| :--- | :--- | :--- | :--- |
| **Corporate Data Model** | `corporate-data-model.xml` | Defines Foundation Objects (FO) such as Location, Pay Component, and Event Reasons. | Global (All Entities) |
| **CSF Corporate Data Model** | `country-specific-corporate-data-model.xml` | Localizes Foundation Objects (e.g., country-specific address formats for Location). | Country-Specific |
| **Succession Data Model** | `succession-data-model.xml` | Defines Employee Data (Person & Employment entities like `personalInfo`, `jobInfo`, `compInfo`). | Global (All Employees) |
| **CSF Succession Data Model** | `country-specific-succession-data-model.xml` | Localizes employee data fields (e.g., National ID formats, localized Job Info fields). | Country-Specific |

---

### 3.2 Key XML Elements & Attributes

When modifying XML data models, each field definition relies on specific structural attributes:

* **`id`**: Unique identifier corresponding to the database column (e.g., `custom-string1`, `standard-hours`).
* **`max-length`**: Maximum character count allowed for user input.
* **`required`**: Boolean flag (`true`/`false`) defining whether the field is mandatory.
* **`visibility`**: Controls access level across three states:
  * `none`: Completely hidden from the UI.
  * `view`: Read-only for all users unless overridden by RBP.
  * `both`: Visible and editable in the UI.
* **`allow-import`**: Determines if the field can be populated via data import files.
* **`<picklist-id>`**: References a legacy picklist or MDF Picklist Code to populate dropdown options.
* **`<label>`**: UI display name, supporting multiple language tags (e.g., `xml:lang="en-US"`).

---

Below is a complete XML block for defining a classic Foundation Object (`Location`) with status, time zone, and address fields:

```xml

      <label>Description</label>

    </field>

  </corporate-data-model>

6. Business Configuration UI (BCUI) Governance

Modern implementations transition direct XML updates to Manage Business Configuration (BCUI) in Admin Center:

Field Synchronization: Updates in BCUI immediately reflect in the backend SDM without requiring Provisioning XML export/import cycles.

Role-Based Permission (RBP) Decoupling: Field visibility set to both in BCUI grants permission targets that are subsequently restricted or enabled per dynamic user group via RBP permission roles.

Trigger Rules Hooks: onChange and onSave business rules attached at the BCUI field level replace legacy hardcoded XML triggers.
